## Purpose and Scope

This page documents the historical and active Architecture Decision Records (ADRs) for the `ciframe` codebase. It outlines the architectural choices regarding deployment mechanisms, data persistence boundaries, and developer workflow constraints. Each record captures the contextual problem, the decision executed, and the technical consequences on components such as `main.py`, the `Dockerfile`, and the AngularJS frontend.

Sources: `docs/adr/0001-local-only-docker-deploy.md:1-16`, `docs/adr/0003-lift-frontend-freeze.md:1-22`

## 1. ADR 0001: Local-Only Docker Deploy

### Context

The repository previously maintained dead deployment configurations targeting legacy cloud platforms: an `app.yaml` file configured for Google App Engine's discontinued `python27` runtime (which required vendoring utilities like `vendor.py` and `appengine_config.py`), and a `Procfile` targeting Heroku [docs/adr/0001-local-only-docker-deploy.md:1-7]. Both prior Heroku endpoints returned 404 errors, and App Engine standard environments had evolved to use modern `entrypoint`-based configurations [docs/adr/0001-local-only-docker-deploy.md:3-7]. Maintaining these multi-cloud targets introduced maintenance overhead without offering a functional deployment path.

### Decision

All legacy cloud descriptors and vendoring artifacts (`app.yaml`, `Procfile`, `vendor.py`, `appengine_config.py`, `lib/`) were purged. They were replaced with a single production-aligned `Dockerfile` [docs/adr/0001-local-only-docker-deploy.md:9-12].

*   The image uses the `python:3.9-slim` base layer [`Dockerfile:1-1`].
*   Dependencies are installed from `requirements.txt` [`Dockerfile:5-6`].
*   The app is served locally via `gunicorn` bound to port `8080` [`Dockerfile:10-12`] using the WSGI entrypoint `main:app`.
*   Cloud targets are intentionally left undecided to avoid vendor lock-in [docs/adr/0001-local-only-docker-deploy.md:14-16].

### Consequences

*   **Single Deployment Artifact**: Local execution and containerized delivery mirror each other via Docker [AGENTS.md:20-25].
*   **Unchanged Backend Architecture**: The core application logic remains a single file (`main.py`) loading `data/top/dataset_final.csv` into memory [AGENTS.md:9-11].
*   **Port Mapping**: Production and containerized environments expose port `8080`, whereas raw virtualenv executions default to port `5000` via Flask's development server [AGENTS.md:31-32].

## 2. ADR 0002: Persistence for Custom Chord Sequences

### Context

Historically, chord sequence discovery relied strictly on pre-computed static tags (`SEQ_FAMOSA` / `seqs_famosas`) ingested from `dataset_final.csv` matching hardcoded sequences defined in `main.py` [docs/features/sequencias-customizadas/01-research.md:9-14]. As part of full-stack feature requirements (see `docs/features/sequencias-customizadas/00-enunciado.md`), users need the ability to define, submit, and persist custom chord sequences rather than depending solely on hardcoded arrays [AGENTS.md:13-15].

However, because the architecture avoids external database services to maintain a lightweight, local-only container footprint, persisting custom user sequences requires evaluating embedded storage options compatible with the single-container model [docs/features/sequencias-customizadas/01-research.md:22-26].

### Decision

The decision path for persistence explores lightweight embedded storage engines (such as SQLite or flat-file JSON serialization) that operate entirely within the local container workspace without requiring external daemon processes or modifying the core `Dockerfile` setup beyond volume mounts. Real-time matching algorithms evaluate user-submitted sequences against `musica.acordes` or `musica.cifra` directly when static tags are absent [docs/features/sequensen-customizadas/01-research.md:9-16].

### Consequences

*   **No External Database Dependency**: Preserves the local-only deployment model established in ADR 0001.
*   **Algorithmic Shift**: Extends matching logic beyond pre-computed CSV tags to compute sequence intersections and order validation in real time.
*   **Frontend Alignment**: Replaces hardcoded client-side sequence lists (`sequencia1` through `sequencia4` in `static/assets/js/controllers/sequencia.js`) with dynamic API interactions [docs/features/sequencias-customizadas/01-research.md:27-33].

## 3. ADR 0003: Lift the Frontend Freeze

### Context

`AGENTS.md` previously instructed contributors against touching or upgrading the AngularJS 1.4.9 + jQuery frontend [AGENTS.md:12-13] "in passing," citing `docs/adr/0001-local-only-docker-deploy.md` as the underlying rationale [docs/adr/0003-lift-frontend-freeze.md:1-4]. This citation was historically imprecise: ADR 0001 addressed containerized deployment and dead cloud targets, making no assertions regarding frontend maintenance constraints [docs/adr/0003-lift-frontend-freeze.md:5-9]. The frontend had remained untouched simply due to a lack of prior task requirements rather than a formal architectural freeze [docs/adr/0003-lift-frontend-freeze.md:11-15].

### Decision

The restriction against touching the legacy AngularJS frontend is explicitly lifted [docs/adr/0003-lift-frontend-freeze.md:17-21].

*   The stack remains legacy AngularJS 1.4.9 + jQuery loaded from CDN in `static/index.html` without a build step [AGENTS.md:12-14].
*   Codebase modifications are permitted when full-stack tasks (such as managing custom chord sequence views or updating route controllers in `static/assets/js/routes.js`) necessitate UI changes [docs/adr/0003-lift-frontend-freeze.md:11-21].
*   Wholesale framework modernization (e.g., migrating to modern Angular or React) remains out of scope for this decision [docs/adr/0003-lift-frontend-freeze.md:19-21].

### Consequences

*   **Full-Stack Feature Delivery**: Enables implementation of user-facing features requiring controller and template updates (e.g., `static/templates/sequencia.html` and `static/assets/js/controllers/sequencia.js`) [docs/features/sequencias-customizadas/01-research.md:27-33].
*   **Maintained Stack Boundaries**: Preserves the legacy client architecture while removing artificial workflow roadblocks for developers implementing end-to-end features.
